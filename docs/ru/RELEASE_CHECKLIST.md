# Контрольный список выпуска релиза (для сопровождающих)

Процедура описывает публикацию GitHub Releases и обновлений Laundry Monitor
через HACS. Нормативная версия — [английский документ](../en/RELEASE_CHECKLIST.md).

**Merge PR сам по себе не публикует релиз.** Публикация, а также изменение
метаданных старых релизов выполняются отдельно и только по решению
сопровождающего. Контрольный список применим и к RC, и к stable.

## 1. Правила версионирования

- Версии и теги **без префикса `v`**: `X.Y.Z-rcN` (например,
  `0.1.8-rc8`) либо `X.Y.Z` (например, `0.1.8`).
- Git-тег, тег GitHub Release и значение `version` в
  `custom_components/laundry_monitor/manifest.json` **на коммите тега**
  должны строго совпадать.
- Для суффикса `-rcN` обязательно `prerelease=true` (**Set as a
  pre-release**). Для стабильного релиза без суффикса — `prerelease=false`.
- RC нельзя помечать **Latest**. Стабильный релиз может получить Latest
  после проверки; автоматику выбора GitHub надо перепроверять.
- Минимальная поддерживаемая версия Home Assistant задана в `hacs.json`.
  Изменение нижней границы требует отдельной проверки совместимости.
- Версию повышаем **один раз в PR подготовки релиза**, а не в каждом PR
  с исправлением issue. Не публикуем релиз из незамерженной feature-ветки.
- Для каждого релиза необходимы текст GitHub Release и датированный
  раздел `CHANGELOG.md`. Историю старых RC не реконструируем задним числом.

## 2. Выбор состава релиза

- [ ] Определить предыдущий **опубликованный** GitHub Release, а не просто
      последний коммит или тег.
- [ ] Сопоставить изменения текущего кандидата с предыдущим
      опубликованным тегом; не включать повторно уже выпущенные исправления.
- [ ] Определить тип: **RC**, если требуется дальнейшее полевое
      тестирование, или **stable**, если поведение проверено. Зелёный CI
      не равнозначен успешной полевой проверке.
- [ ] Проверить открытые регрессии и ограничения детекторов, восстановления
      после перезапуска, диагностики и Recorder.
- [ ] Выбрать новую уникальную версию. Опубликованные теги не переиспользовать
      и не передвигать принудительно.

## 3. PR подготовки релиза

- [ ] Создать ветку от текущего `main` (например,
      `release/0.1.8-rc8`). Изменить версию manifest и необходимые
      релизные материалы; не смешивать с функциональными исправлениями.
- [ ] Перенести **подтверждённые** изменения из `[Unreleased]` в
      `CHANGELOG.md`, оформив раздел `## [X.Y.Z-rcN] - YYYY-MM-DD`
      или `## [X.Y.Z] - YYYY-MM-DD`. Не придумывать результаты полевых
      проверок и не скрывать последствия для пользователей.
- [ ] Подготовить текст GitHub Release в отдельном локальном файле.
      Рекомендуемые разделы (удалить все заполнители перед публикацией):

      ```markdown
      ## Changes / Изменения
      - Исправления, функции, ссылки на PR и issues.

      ## Compatibility and upgrade notes / Совместимость
      - Минимальная версия HA Core, реально проверенные версии Core,
        изменения сущностей, миграции либо «Нет».

      ## Validation / Проверки
      - Ссылка на CI и коммит, HACS/Hassfest, проверка установки и
        обновления, только фактически выполненные полевые тесты.

      ## Known limitations / rollback / Ограничения и откат
      - Открытые риски, способ вернуться к предыдущему релизу.
      ```

- [ ] Убедиться, что на **актуальном HEAD** PR зелёные
      `Tests (minimum)`, `Tests (current)`, агрегирующий `Tests`,
      `Ruff check`, `Hassfest` и `HACS`.
- [ ] Проверить вывод CI с версиями Core; не объявлять проверенной версию,
      которую тесты на самом деле не запускали.

Перед публикацией, после подготовки manifest, changelog и файла release
notes, вручную запустить **проверку без изменений файлов** (`false`
вместо `true` для стабильного выпуска):

```bash
python scripts/verify_release.py \
  --tag 0.1.8-rc8 \
  --prerelease true \
  --notes-file /path/to/release-notes.md
```

Номер выше — **пример**, а не команда публиковать именно эту версию.

## 4. Проверка установки, обновления и полевой работы

- [ ] На тестовом HA с резервной копией проверить установку/переустановку
      из HACS в нужном канале. Для RC может потребоваться включить
      переключатель получения предварительных версий репозитория.
- [ ] Проверить **обновление** с предыдущего опубликованного релиза,
      перезапуск HA, Config Flow/Options, сохранность сущностей, логи и
      Repairs.
- [ ] Проверить **чистую установку**: минимальная конфигурация с датчиком
      мощности, при необходимости — датчики вибрации/тока/нагрева.
      Проверить диагностику и переводы.
- [ ] Проверить восстановление snapshot после перезапуска. При изменении
      поведения детекторов — наблюдать хотя бы один реальный цикл с
      диагностикой; записывать только фактически выполненные проверки.
- [ ] Проверить, что RC не предлагается пользователям HACS без подписки
      на предварительные версии. При неожиданном поведении обновления или
      отката не продолжать публикацию до выяснения причины.
- [ ] До обновления рабочего HA сделать резервную копию; изменения
      истории Recorder не считать автоматически ошибкой runtime.

## 5. Тег и публикация (после merge)

- [ ] Объединить проверенный release-PR в `main` и дождаться успешного
      **Validate именно на итоговом коммите main**. Установить тег на
      этот проверенный коммит, а не на старый HEAD ветки при
      squash-merge — SHA мог измениться.
- [ ] Сверить manifest на коммите публикации. В GitHub открыть
      **Releases → Draft a new release → Choose a tag → Create new tag
      on main**, указать нужный коммит main.
- [ ] Добавить проверенные release notes. Для RC включить **Set as a
      pre-release**, для stable не включать; RC не назначать **Latest**.
- [ ] Опубликовать именно **GitHub Release**: одного Git-тега для
      используемой схемы версионирования HACS недостаточно.
- [ ] Проверить опубликованную страницу: тег, коммит, описание, отметку
      Pre-release (или её отсутствие) и Latest.
- [ ] Проверить результат workflow
      `Audit published release / Release metadata`. Он запускается
      **после** публикации и не предотвратит ошибочный релиз; ручная
      preflight-проверка обязательна. Workflow сверяет тег, manifest,
      changelog, notes, тип релиза и достижимость коммита из `main`.
- [ ] Проверить канал и установку/обновление в HACS, затем отслеживать
      сообщения об ошибках. Зафиксировать тег, дату, ссылку на CI,
      результаты smoke/field testing.

## 6. Действия при ошибочном релизе

Если релиз неисправен, определить круг затронутых пользователей и
подготовить **новую** исправленную версию с новым тегом. Не удалять
и не переносить опубликованные теги через force-push: HACS и клиенты
могут кэшировать их содержимое. Пользователям описать выбор предыдущего
исправного опубликованного релиза в HACS и восстановление из backup,
если потребуется. Ошибочный флаг prerelease исправлять осознанно с
проверкой поведения HACS и описанием последствий.

## 7. Метаданные старых RC (отдельное решение)

По issue #17 релизы от `0.1.8-rc3` до `0.1.8-rc7` опубликованы с
`prerelease=false`, несмотря на суффикс RC. При внедрении этой процедуры
**не изменять** их теги, коммиты и файлы релиза. Не исправлять флаг
массово без проверки существующих установок HACS: выбор доступной версии
может измениться, особенно пока нет стабильного релиза. К вопросу о
корректировке исторических метаданных вернуться отдельно после проверки
обновлений и выбора версий в HACS. Все **новые** RC должны иметь
`prerelease=true`.

См. [руководство HACS по версиям](https://hacs.dev/docs/publish/start/)
и [правила marketplace](https://contributors.home-assistant.io/marketplace/how-it-works/).
