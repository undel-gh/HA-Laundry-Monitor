# Laundry Monitor 0.1.8

**First stable 0.1.8 release** — a field-validated Home Assistant integration
for passive washing-machine cycle monitoring.

This release promotes the 0.1.8 RC line to stable. The most recent published
candidate is [0.1.8-rc8](https://github.com/undel-gh/HA-Laundry-Monitor/releases/tag/0.1.8-rc8).
**The summary below covers changes accumulated since the last plain-version
stable release, 0.1.4**, including earlier 0.1.5–0.1.8 candidates; it is
**not** a list of new runtime changes since rc8. The only merged change
after rc8 was CI/test-tooling compatibility [#26](https://github.com/undel-gh/HA-Laundry-Monitor/pull/26).

Laundry Monitor observes existing Home Assistant sensor entities. It does
not control the washing machine, smart plug or appliance programs.

## Changes

### Washing-cycle detection

- **Heating-aware final-spin detection.** Optional vibration and
  experimental hybrid electrical corroboration distinguish active heater
  operation from a likely terminal spin. A non-heated fast path can help
  with short programs, without treating absent heating as proof of spin.
  Hybrid thresholds must be calibrated for the individual machine.
- **Protection against heated-cycle false positives.** With hybrid
  confirmation enabled and heating previously detected, even full
  vibration evidence needs electrical corroboration. The electrical
  spin candidate must be sustained for at least **45 seconds** and
  followed by a qualifying new vibration rising edge at or after its
  start. [#1](https://github.com/undel-gh/HA-Laundry-Monitor/pull/1)
- **Two finish-confirmation paths** remain: confirmation after
  `final_spin` and a conservative inactivity fallback if terminal
  spin was never confirmed.

### Reliability and diagnostics

- **Safer state recovery:** active-cycle snapshots with invalid, absent
  or timezone-naive critical timestamps fail closed instead of
  restoring untrustworthy running state.
  [#8](https://github.com/undel-gh/HA-Laundry-Monitor/pull/8)
- **Unit-aware power/current processing:** supported HA source units
  are normalized to W/A; unsupported units, invalid values or
  non-finite conversions are not silently treated as W/A. Optional
  current-source errors do not block required power-based monitoring.
  [#9](https://github.com/undel-gh/HA-Laundry-Monitor/pull/9)
- **Fresh electrical observations:** valid repeated HA reports of
  unchanged power/current readings are recognized by the electrical
  detector; duplicate vibration reports do not invent new OFF-to-ON
  events. [#10](https://github.com/undel-gh/HA-Laundry-Monitor/pull/10)
- **Consistent source diagnostics:** `sources[*].available` reflects
  whether a reading is usable by Laundry Monitor, while
  `sources[*].entity_available` describes Home Assistant state
  availability. Repairs and runtime use consistent unit checks.
  [#18](https://github.com/undel-gh/HA-Laundry-Monitor/pull/18)
- **Clarified `error` state:** a monitoring or required-input
  reliability problem, **not** a washing-machine error code.
  [#11](https://github.com/undel-gh/HA-Laundry-Monitor/pull/11)

### Duration and Recorder behavior

- New `sensor.<device>_cycle_started_at` exposes the active cycle
  start time. A compatible frontend can calculate elapsed time locally,
  without emitting periodic Home Assistant states.
- The existing `current_cycle_duration` is **not** a live ticking
  sensor: it is a snapshot updated on significant cycle transitions.
  It and other high-frequency diagnostic entities are disabled by
  default for **new** installations; existing registry selections
  are preserved.
- Unchanged diagnostic states are no longer needlessly published.
  Detector evaluation cadence is **not reduced**.
  [#19](https://github.com/undel-gh/HA-Laundry-Monitor/pull/19)

## Compatibility and upgrade notes

- **Minimum Home Assistant Core: 2026.6.0**, unchanged.
  Full automated CI regression suites are configured for
  **2026.6.0**, **2026.10.4** and **2026.11.1** with corresponding test
  fixture packages. The Core 2026.11.1 official
  `pytest-homeassistant` support is test infrastructure only.
  [#22](https://github.com/undel-gh/HA-Laundry-Monitor/pull/22)
  [#26](https://github.com/undel-gh/HA-Laundry-Monitor/pull/26)
- **Existing dashboards:** if you relied on
  `current_cycle_duration` updating continuously, switch to
  `now - cycle_started_at` computed **in the frontend** during
  `running` and `final_spin`; show `last_cycle_duration`
  after completion. Avoid a minute-updated HA template sensor
  solely to display elapsed time.
- **External Diagnostics consumers:** update parsers if they
  interpreted `sources[*].available` as simple HA entity
  availability; use `entity_available` for that distinction.
- The only mandatory input remains the power sensor. Current,
  vibration, door, leak, energy and plug switch are optional.
  No entity rename or config migration is introduced by this
  release-preparation change.
- **HACS release channels:** RCs `0.1.8-rc3` through `rc7`
  were historically published as ordinary GitHub Releases, despite
  their RC suffix; `rc8` was correctly published as a prerelease.
  **0.1.8 must be published without the Pre-release flag**
  (`prerelease=false`) and should be confirmed to appear on the
  stable HACS channel. Existing RC tags and metadata are not
  rewritten. Allow for normal HACS refresh delays.
- The separately maintained
  [Laundry Monitor Card](https://github.com/undel-gh/Laundry-Monitor-Card)
  is a separate frontend project; this integration release does not
  install or upgrade the card.

## Validation

- The integration was observed in **four field cycles on 14, 15,
  18 and 21 November 2026** in the supplied Home Assistant
  history: a heated long program, shorter non-heated programs,
  `vibration_only` and `hybrid` terminal-spin confirmation, and
  successful completion/return to idle. A required-power-source
  availability interruption and recovery were also observed.
  These are practical observations, **not** a calibrated physical
  ground-truth evaluation of exact drum motion or completion time.
- The supplied 23 November diagnostics were captured on Home
  Assistant **2026.10.1**, with all required sources available at
  that instant. They are an `idle` snapshot and do not reconstruct
  historical internal `spin_gate_reason` decisions.
- The existing
  [Validate workflow](https://github.com/undel-gh/HA-Laundry-Monitor/actions/workflows/validate.yml)
  includes three Core regression targets, aggregate Tests, Ruff,
  Hassfest and HACS. Exact release-PR and **post-merge main commit**
  CI evidence must be recorded in the reviewed PR/release checklist
  before publication.
- **Not yet claimed complete at draft preparation:** fresh stable-channel
  HACS install, upgrade from a prior published RC, restart/snapshot
  recovery smoke, and stable-channel update visibility. Perform and
  record these checks on a backup-enabled HA instance before publishing.
  A green CI run alone is insufficient.

## Known limitations and rollback

- Hybrid spin confirmation is optional/experimental, requires machine-
  specific calibrated thresholds and sufficiently fresh sensor reports.
  Battery vibration sensors may not expose every physical event. A
  cycle may therefore finish through the conservative running-state
  inactivity fallback even when no `final_spin` was confirmed.
- A repeated Home Assistant `state_reported` event does not prove
  the physical device took a new measurement.
- `error` is not an appliance diagnosis. No precision guarantee
  about the exact physical terminal-spin or melody moment is made.
- Open [issue #3](https://github.com/undel-gh/HA-Laundry-Monitor/issues/3)
  (spin-policy refactor) and
  [issue #15](https://github.com/undel-gh/HA-Laundry-Monitor/issues/15)
  (partial corrupt-snapshot recovery) are post-stable work,
  not observed blocking regressions.
- Before upgrading, back up Home Assistant. For an affected
  installation, choose a previously known-good published version
  in HACS (where the configured channel makes it available) and
  restore the HA backup if necessary. Do **not** rewrite published
  tags or release assets.

Publication contract: the reviewed release-preparation PR must be
merged first; verify the resulting `main` CI; then tag **0.1.8**
at that verified main commit and publish a GitHub Release with
